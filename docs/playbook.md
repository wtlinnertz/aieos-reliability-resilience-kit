# Reliability & Resilience Kit — Playbook

This playbook defines the end-to-end process for the Reliability & Resilience Kit (Layer 6). It covers how to move from a frozen Release Record to governed reliability operations: SLO definition, incident management, and periodic health reporting.

---

## Artifact Flow

```
Upstream: Frozen Release Record (RR) §7 from Release & Exposure Kit (Layer 5)
         │
         ▼
Step 0: Service Reliability Entry Record (SRER) — human-authored
         │ Validate → Freeze
         ▼
Step 1: Service Reliability Profile (SRP) — generated
         │ Validate → Freeze
         │ (versioned; reused until SLOs change — see SRP Revision Protocol)
         ▼
Step 2: Active Operation (human + monitoring tooling)
         │ Incidents trigger Step 3
         ▼
Step 3: Incident Record (IR) — generated, per incident
         │ Validate → Freeze
         ▼
Step 4: Reliability Health Report (RHR) — generated, periodic
         │ Validate → Freeze
         ▼
Handoff to Layer 7 (Insight & Evolution)
```

Steps 3 and 4 repeat for each incident and each review period respectively. The frozen SRP is the constant reference point.

---

## Upstream Interface

**Upstream:** Release & Exposure Kit (Layer 5)
**Input:** Frozen Release Record (RR), specifically §7 Handoff to Layer 6

The RR §7 must contain:
- What is in production (system, version, deployed configuration)
- Current exposure state
- Monitoring active (metrics, dashboards, alert configurations, thresholds)
- SLO baseline (sourced from ORD or first-release documentation)
- Open incidents at handoff time
- Recommended watch items

If RR §7 is absent or incomplete, do not begin the entry gate. Request a corrected RR from the upstream release owner.

---

## Step 0 — Service Reliability Entry Gate

**Artifact:** Service Reliability Entry Record (SRER)
**Type:** Human-authored entry gate
**Spec:** `docs/specs/srer-spec.md` (5 hard gates)
**Template:** `docs/artifacts/srer-template.md`
**Validator:** `docs/validators/srer-validator.md`

### Purpose

The SRER confirms the upstream handoff is complete, identifies the reliability owner, and establishes the monitoring baseline before SRP generation begins. It is not generated by AI — the reliability owner completes it.

### Inputs
- Frozen Release Record (RR)

### Process

1. The reliability owner obtains the frozen RR from the Release & Exposure Kit.
2. Using the SRER template, the owner completes all sections: upstream reference (capturing RR §7 fields), reliability owner contact, SLO baseline from RR §7, and monitoring confirmation.
3. The owner verifies that every monitoring item listed in RR §7 is active — checking the monitoring system directly, not just trusting the RR.
4. The owner records alert thresholds for each active alert and documents any gaps.
5. The completed SRER is validated in a separate session from the one that completed it.
6. On PASS: the reliability owner reviews and freezes the SRER. **No SRP generation may begin until the SRER is Frozen.**
7. On FAIL: address blocking issues and re-validate.

### Freeze Points
- SRER must be Frozen before SRP generation begins

---

## Step 1 — Service Reliability Profile

**Artifact:** Service Reliability Profile (SRP)
**Type:** Generated
**Spec:** `docs/specs/srp-spec.md` (7 hard gates)
**Template:** `docs/artifacts/srp-template.md`
**Intake:** `docs/artifacts/service-reliability-intake-template.md`
**Prompt:** `docs/prompts/srp-prompt.md`
**Validator:** `docs/validators/srp-validator.md`

### Purpose

The SRP defines what "working correctly" means for this service: SLO targets, error budgets, burn rate alert thresholds, and measurement methodology. It is the authoritative reference for all IR and RHR artifacts.

### Inputs
- Frozen SRER
- Completed Service Reliability Intake Form (human-authored)
- `docs/principles/service-reliability-principles.md`

### Process

1. The service team completes the Service Reliability Intake Form. Use the SLO Calibration utility prompt (`docs/prompts/slo-calibration-prompt.md`) if historical data is available and targets are uncertain.
2. In a new AI session, provide: frozen SRER + completed intake form + `docs/specs/srp-spec.md` + `docs/artifacts/srp-template.md` + `docs/principles/service-reliability-principles.md`. Use the SRP prompt (`docs/prompts/srp-prompt.md`).
3. Review the generated SRP. Check that SLO targets are grounded in the SRER baseline and that all metric names are confirmed against the monitoring system.
4. Validate the SRP in a separate session using `docs/validators/srp-validator.md` and the spec.
5. On PASS: human review and freeze. **The frozen SRP is now the active version.**
6. On FAIL: address blocking issues and re-generate or correct; re-validate.

### Freeze Points
- SRP must be Frozen before IRs and RHRs reference it
- Frozen SRP is immutable; see SRP Revision Protocol for change handling

### Reuse
The frozen SRP is reused across all subsequent IRs and RHRs until SLOs change. There is no need to regenerate the SRP for each incident or each review period.

## Step 2 — Active Operation

**Type:** Human + monitoring tooling (no AI artifact produced)

Active operation is the ongoing state of running the service against its SRP. No new artifact is generated during this step.

### Activities during active operation

- **Monitor burn rate alerts**: When a fast-burn or slow-burn alert fires, the on-call responder is paged per SRP §4 routing. The responder investigates whether the burn rate indicates an active incident.
- **Track error budget state**: The team is responsible for knowing whether the current measurement window budget is healthy, at risk, or exhausted.
- **Release governance**: When considering new releases that affect this service, confirm error budget state against the SRP §3 freeze condition before proceeding.
- **Use incident triage when needed**: During active incidents, use `docs/prompts/incident-triage-prompt.md` for structured adversarial analysis.

### When Step 3 is triggered

An Incident Record must be generated when:
- An SLO breach occurs (SLI drops below target for a measurable period)
- A burn rate alert fires and the investigation confirms a degradation event
- A user-visible outage or degradation occurs regardless of alert state
- An incident commander declares an incident of any severity level

---

## Step 3 — Incident Record

**Artifact:** Incident Record (IR)
**Type:** Generated (per incident)
**Spec:** `docs/specs/ir-spec.md` (6 hard gates)
**Template:** `docs/artifacts/ir-template.md`
**Prompt:** `docs/prompts/ir-prompt.md`
**Validator:** `docs/validators/ir-validator.md`

### Purpose

The IR documents one incident from detection through resolution and post-incident review. It is an evidence artifact — it captures what happened, not what should have happened.

### Inputs
- Incident evidence: detection alerts, monitoring data, responder notes, communication logs
- Frozen SRP (the version active during the incident)

### Process

1. During the incident, the incident commander assigns responders and captures events in a running log.
2. After resolution is declared, allow a brief settling period (typically 24–48 hours) before authoring the IR to allow post-incident review discussion.
3. Collect all incident evidence: alert records, metric screenshots, responder notes, decision records.
4. In a new AI session, provide: incident evidence + frozen SRP + `docs/specs/ir-spec.md` + `docs/artifacts/ir-template.md` + `docs/principles/incident-management-principles.md`. Use the IR prompt (`docs/prompts/ir-prompt.md`).
5. Review the generated IR. Confirm the root cause analysis reflects what was actually learned, not what was speculated during the incident.
6. Validate in a separate session using `docs/validators/ir-validator.md` and the spec.
7. On PASS: incident commander reviews and freezes. **The IR is now an immutable record.**
8. On FAIL: address blocking issues. If follow-up actions are the blocker, complete them before freezing.

### Freeze Points
- IRs should be frozen within 5 business days of incident resolution
- A frozen IR is not amended; corrections require a new IR version (IR-{SERVICE}-{NNN}v2)

---

## Step 4 — Reliability Health Report

**Artifact:** Reliability Health Report (RHR)
**Type:** Generated (periodic)
**Spec:** `docs/specs/rhr-spec.md` (5 hard gates)
**Template:** `docs/artifacts/rhr-template.md`
**Prompt:** `docs/prompts/rhr-prompt.md`
**Validator:** `docs/validators/rhr-validator.md`

### Purpose

The RHR is the periodic review artifact. It synthesizes SLO compliance, error budget state, and incident history over a defined coverage period and produces the Layer 7 feed.

### Cadence

The review cadence is determined by the service team and stated in the SRER or the first RHR. Common cadences:
- Monthly: aligned with 30-day SLO measurement windows
- Weekly: for high-criticality services or services with elevated alert activity

### Inputs
- Frozen SRP (active version(s) for the coverage period)
- All frozen IRs from the coverage period (by IR ID)
- Monitoring data for the coverage period (SLO compliance %, error budget consumption, burn rate)

### Process

1. At the end of the review period, collect: all IRs from the period + monitoring data export + active frozen SRP.
2. In a new AI session, provide all inputs + `docs/specs/rhr-spec.md` + `docs/artifacts/rhr-template.md`. Use the RHR prompt (`docs/prompts/rhr-prompt.md`).
3. Review the generated RHR. Confirm compliance percentages match monitoring data and that all IRs from the period are included.
4. Validate in a separate session using `docs/validators/rhr-validator.md`, the spec, and the active SRP.
5. On PASS: review owner reviews and freezes.
6. On FAIL: address blocking issues; re-generate or correct; re-validate.

### Freeze Points
- RHRs should be frozen within 5 business days of the coverage period end
- A frozen RHR is the Layer 7 feed for that period; it is not amended post-freeze

---

## Downstream Handoff

**Downstream:** Layer 7 (Insight & Evolution)
**Handoff artifact:** Frozen RHR — specifically §5 Layer 7 Feed

The Layer 7 Feed provides:
- Reliability trend direction (improving | stable | degrading) with basis
- Systemic issues outstanding from IRs
- Improvement signals observed during the period
- Recommended continued watch items

Layer 7 consumes RHRs across multiple periods to identify evolution patterns. Provide Layer 7 with:
1. All frozen RHRs for the service (in order)
2. The active frozen SRP

Layer 7 does not modify frozen RHRs. If a correction is needed after freeze, issue a corrected RHR version.

## Freeze Points Summary

| Artifact | When Frozen | What It Gates |
|----------|------------|---------------|
| SRER | Before SRP generation | SRP generation |
| SRP | After validation | IR and RHR generation; releases affecting this service (per §3 freeze condition) |
| IR | Within 5 business days of resolution | RHR (IRs must be frozen before the RHR that covers their period is generated) |
| RHR | Within 5 business days of period end | Layer 7 handoff |

## SRP Revision Protocol

When SLO targets, error budget policy, or measurement methodology must change:

1. **Do not edit the frozen SRP.** The frozen SRP remains immutable.
2. The service team identifies the trigger: post-incident review finding, user feedback, contractual requirement change, or organizational decision.
3. The team completes a new intake form reflecting the changes.
4. Generate a new SRP version (v2, v3, etc.) using the SRP prompt with the updated intake.
5. Validate and freeze the new SRP version.
6. All subsequent IRs and RHRs reference the new version. In-progress review periods that span the version change must report compliance separately per version sub-period.
7. Downward revisions (lower targets) require explicit authorization from the service owner and the reliability owner. The business justification must be documented in the new SRP.

## Session Discipline

Follow these rules in every AI session:

| Rule | Why |
|------|-----|
| One artifact per session | Prevents context contamination across artifacts |
| Separate generation and validation sessions | Prevents self-validation bias |
| Include full frozen upstream artifacts | Do not summarize; the AI needs complete context |
| Include spec and template for generation sessions | The AI generates against the spec, not from memory |
| Include spec and validator for validation sessions | The validator judges against the spec, not against the generated content |

Do not ask the AI that generated an artifact to also validate it in the same session.

---

## Re-Entry Protocol

When a frozen artifact must be corrected:

1. Identify the artifact to be changed (SRER, SRP, IR, or RHR).
2. Identify all downstream artifacts that reference it or depend on it.
3. Assess the impact: does the change affect IR or RHR conclusions? Does it change error budget calculations or SLO compliance assessments?
4. Issue a new version of the artifact (e.g., SRP v2, IR-SERVICE-001v2).
5. Re-validate the new version.
6. Re-validate all affected downstream artifacts that reference the changed artifact.
7. Document the change in the new version's document control section with a reference to the original and the reason for the correction.

---

## Abort Protocol

If the entry gate (SRER) reveals that the RR §7 handoff is incomplete:

1. Do not proceed with SRP generation.
2. Document the gap in the SRER §5 monitoring confirmation or §4 SLO baseline as a missing item.
3. Contact the upstream release owner and request completion of RR §7.
4. Hold Layer 6 intake at the SRER step until the gap is resolved.

If active operation reveals that monitoring coverage is insufficient to calculate SLO compliance:

1. Document the coverage gap in the current RHR with dates and reason.
2. Create an IR for any incidents that occurred during the coverage gap if the gap was caused by or contributed to an incident.
3. Do not report SLO compliance for periods where data is unavailable — document the gap instead.
4. Initiate instrumentation improvement as a follow-up action in the current period.

---

## Amendment Procedure

A frozen artifact may be corrected in place without re-validation when **all** of the following criteria are met:

1. The correction does not affect any field evaluated by a hard gate.
2. The correction does not change scope, decisions, owners, or technical specifications.
3. The correction does not affect any field referenced by a downstream artifact.

**Procedure:** Make the correction and add an Amendment Log entry to the artifact's Document Control section: date, what changed, materiality criterion cited, and who authorized the change. No re-validation is required.

**If there is any ambiguity** about whether a change is non-material, treat it as material and issue a new artifact version. The amendment path must not become a workaround for the version protocol.

## Escalation Paths

This kit is the primary escalation source in the AIEOS system. SEV1/2 incidents and recurring reliability patterns may warrant upstream re-entry in EEK or PIK.

### Trigger 1 — SEV1/2 Incident with Code Defect (to EEK)

**Signal:** An Incident Record documents a SEV1 or SEV2 incident whose root cause is a code defect — not a configuration error, capacity event, or external dependency failure.

**When to assess:**
- After an IR is frozen for any SEV1 or SEV2 incident
- Use the escalation assessment prompt (`docs/prompts/escalation-assessment-prompt.md`) to evaluate whether the trigger criteria are met

**Trigger criteria (all must be true):**
1. The incident severity was SEV1 or SEV2 (see `incident-management-principles.md` §1 for definitions)
2. The root cause was a code defect (not configuration, capacity, or external dependency)
3. The defect is in a system whose implementation is governed by the Engineering Execution Kit

**What to do when triggered:**
1. The reliability owner reviews the frozen IR and confirms the trigger criteria.
2. Create an escalation record: trigger type (Trigger 1), triggering IR ID, defect description (the specific code defect from the IR root cause section), affected system, and recommended action.
3. Send the escalation record to the EEK team. They will create a Kit Entry Record and handle the fix.
4. Track the EEK defect fix in the next RHR (reference the IR and the EEK fix ticket in the RHR follow-up actions section).

**A human must authorize** the escalation decision.

### Trigger 2 — Recurring Reliability Pattern (to PIK)

**Signal:** Three or more consecutive RHRs for the same service identify the same root cause class in the systemic issues section, with no evidence of effective remediation between review periods.

**When to assess:**
- When generating an RHR and the systemic issues section shows a recurring pattern
- Use the escalation assessment prompt to evaluate whether the trigger criteria are met

**Trigger criteria (all must be true):**
1. Three or more review periods have documented the same root cause class (not just the same symptom)
2. Each period shows the pattern was present (not just lingering from a prior period)
3. Prior period follow-up actions either were not completed or did not eliminate the pattern

**What to do when triggered:**
1. The review owner confirms the pattern by comparing the current RHR against the two prior RHRs.
2. Create an escalation record: trigger type (Trigger 2), triggering RHR ID (and prior RHR IDs), pattern description (the recurring root cause class), affected service, and recommended action.
3. Send the escalation record to the PIK team as discovery intake context. The PIK team assesses whether a new discovery engagement is warranted.
4. Document the escalation in the current RHR's follow-up actions section: "Escalation record sent to PIK team — reference [escalation record ID]."

**A human must authorize** the escalation decision. The judgment that three occurrences constitute a systemic pattern vs. coincidence requires human assessment.

## Principle File Revision

When a principle file in `docs/principles/` changes, use the change categories defined in `aieos-spec/docs/principle-file-standard.md`:

| Change Category | Version Bump | Re-Entry Impact |
|----------------|-------------|-----------------|
| **Minor** (clarification only) | `v_.x → v_.x+1` | No re-entry required; already-frozen artifacts remain valid |
| **Significant** (new requirement or tightened constraint) | `v1.x → v1.x+1` | Review artifacts generated after the change against updated principles; already-frozen artifacts are grandfathered |
| **Breaking** (removal or loosening) | `vN.x → vN+1.0` | Requires service owner authorization and documented business justification; re-entry may be warranted |

Every change to a principle file must bump the version field, even minor clarifications.
